tronzero · design notes · 14 Nov 2026 · two to four players

An AlphaZero agent for CodinGame Tron, built on slinky's lessons

One small network learns move priors and a value for every bike from its own games of two, three and four players. A PUCT search plays with them. The search and the network run in a dependency-free Rust engine, the same code for self-play and for play, and JAX on the GPU does only the training.

The loop

slinky runs self-play, search and learning as one JAX program. Here the game and the search are native code from the start, because the agent must end up as a single Rust file that searches on one CPU core in under 100 ms. Writing that engine first means the code that generates training games is the code that will play.

Turns are sequential, so every node has one mover

Battlesnake moves are simultaneous, which is why slinky's search is decoupled: each snake picks its move at a node without seeing the others'. CodinGame Tron is not like that. Bikes move one at a time in seat order, each having seen the moves before it. So every node of the tree belongs to one bike, and that bike picks the move that is best for itself.

With two bikes that is ordinary alternating PUCT. With three or four there is no single value to negate, so a node keeps one value per bike and the backup adds the leaf's values unchanged (the maxn rule). A leaf is one of three things, and only one of them costs a network evaluation.

A value is a placement

The network gives every bike still in the game a value in [−1, 1]: +1 for winning, −1 for being the next one out, evenly spaced between. In a duel that is the usual win or loss.

The network answers on the scale of the position it is shown. When bikes have died between the root and a leaf, the search maps the leaf's values onto the root's scale, so a bike that has outlasted one of four can no longer score below −⅓. slinky's rescale_q does the same job for its duel values. The target is placement, not only winning, because CodinGame ranks a multi-player game by finishing order.

A dead bike's trail leaves the board

A bike that cannot move when its turn comes is out and its trail disappears. That changes what a cut-off means. Between the last two bikes it is final: once no empty cell is reachable by both, the mover wins if it can make more moves than the other (it moves first, so a tie loses), and the search values that as tanh((a − b − ½) / 3) from the alpha-beta engine's fill estimator. Self-play adjudicates such games with the primed greedy fill and stops.

With three or more bikes a death can reopen the board, so the game goes on. A bike alone in its region while others still share space takes the greedy space-filling step from the existing engine, and a bike with one legal move takes it. The search passes through both kinds of position without a choice and without a network evaluation, up to six in a row, so a simulation ends at a position where someone has a decision. At play time an isolated agent uses the full primed fill.

What the network sees

Sixteen planes, all zero off the board

  • 0Empty cell
  • 1–3Head of each other bike, in turn order after the mover
  • 4–7Cells each bike reaches first (a tie goes to the bike that moves sooner)
  • 8–11How close each bike is: (64 − distance) / 64
  • 12–15Each bike's trail: the cells that come back if it dies

Thirteen scalars go straight to the hidden layer: each bike's territory and reachable counts, the share of the board still empty, how many bikes are left, and the mover's territory lead over its best rival.

Bikes are always listed from the mover onwards in turn order, so the network never sees seat numbers, and a game that has come down to two bikes looks like a duel with the other planes empty. The policy head speaks for the mover; the value head has one output per listed bike.

The distance planes are the one place this departs from learning on raw boards. Who reaches a cell first needs a flood fill, which a few small convolutions cannot compute, and the engine gets all four distance maps from bitboard waves in under 4 µs. With them the network starts from what the Voronoi heuristic knows and learns the corrections.

A network sized for a 100,000-character paste

CodinGame takes one source file of at most 100,000 characters, weights included, and gives one core 100 ms. Both limits point the same way: a network small enough to pack into the paste is also fast enough to search with. Going from two players to four changed only the input planes and the value head, about 2,400 parameters.

Three things are checked outside training. The Rust forward pass and the JAX one agree on 512 random positions with two, three and four bikes alive (identical distance maps, outputs within 4 × 10−7). The rules hold their invariants over 30,000 random games. And through the existing referee, sprt.py, the agent's every death in 144 games at two, three and four players was a real trap: no illegal move, no timeout, so its picture of the board matches the referee's, vanishing trails included.

The agent is ahead in every format. In four-player games it finishes ahead of a given alpha-beta engine 64% of the time and is the first bike out in 60 games of 800, against 200 at par. The roles reversed tell the same story: one alpha-beta engine among three agents (200 games at 20 ms) scored 0.295 ± 0.045 on placement, won 15.5% and was first out in 109 games.

Its share of outright wins is above par by less. In process, on 200 random openings, it won 29.4%. Through the existing referee, with the engines as separate processes, it won 243 of 720 (33.8%) over three seeds of the referee's 60 book openings: 87, 74 and 82 of 240. The two harnesses agree within their noise. The first of those seeds alone gave 88 to 92 of 240 in four earlier runs, which is where an earlier version of these notes got 37.5%: which openings are played matters more than which harness plays them. Those earlier runs also had the frame-reader bug described under the paste; the in-process matches never did.

The agent reaches the last two in about 70% of games, where par is 50%, but arrives with less territory more often than not, and whoever is ahead at that moment wins 96% of the time. A likely reading, not yet tested: it survives positions a weaker bike would have died in, and the alpha-beta engine it then meets is the best placed of three. The training target makes this a fair trade, since second of four is worth +⅓. A target that pays more for first place would trade placements for wins.

The paste: one Rust file of 95,566 characters

CodinGame takes a single source file. tools/make_paste.py builds it from the engine's own sources, so the file that plays on CodinGame is the code measured above: the board, the forward pass, the search and the play loop, each wrapped in a module, with comments, indentation and the training-only code removed, and the weights appended as one string. The result is paste/tronzero_paste.rs.

The two kinds of layer tolerate rounding very differently. The hidden layer holds nine tenths of the weights and is fine at 7 bits. The small layers are not fine at 8: the first convolution, the scalar inputs and the two heads each move the outputs when rounded that coarsely, and together they shift some value outputs by half the value range. They are a tenth of the weights, so 12 bits for them costs 3,700 characters and brings the error down to what the hidden layer alone causes.

What the engine needed before it could be pasted

  • Kernels chosen when the program starts. The AVX2 and FMA kernels run only if the processor reports both; otherwise plain loops compute the same network at about half the speed.
  • A deadline that adapts. The search stops when two more steps as long as its slowest so far would not fit. CodinGame's arena compiles Rust with optimisation, but its IDE does not, and there one simulation takes about 3 ms instead of 30 µs. A check every so many simulations would have timed out; this one stays inside 100 ms with a couple of dozen simulations.
  • A move without search. If not one simulation fits, the legal move with the highest prior is played.
  • Buffers on cache lines. The kernels read 32 bytes at a time, and the allocator only promises 16-byte alignment. Whether the weights landed aligned changed from one build to the next: the paste ran 12% slower per simulation than the engine with identical code. Weights and activations now start on 64-byte boundaries, and the two builds are within 2% of each other.

A bug the referee found: a head erased with a dead bike's trail

The referee's log showed three such crashes in 1,200 games of the paste, and a saved game reproduced one move for move. tools/paste_check.py now starts with a scripted position that fails on the old reader and passes on the new one.

Nothing here has run on CodinGame. Three things only a submission can show: that its editor counts the file as 95,566 characters (it is 211,932 bytes as UTF-8), which Rust version compiles it, and how many simulations its machines manage in 95 ms. The paste prints that count to stderr every turn, and its two time budgets are constants at the top of the file.
